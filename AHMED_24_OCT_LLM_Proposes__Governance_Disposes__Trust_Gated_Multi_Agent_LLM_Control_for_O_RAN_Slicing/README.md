# LLM Proposes, Governance Disposes — IEEE WCNC paper (LaTeX + reproducible artefacts)

## Layout
```
main.tex              6-page IEEEtran conference paper (pdfLaTeX, Overleaf-ready)
references.bib        18 references, each checked against Crossref/arXiv/ACL Anthology
IEEEtran.cls/.bst     IEEE class + style (Overleaf already provides them; kept for local builds)
figures/arch.tex      Fig. 1 architecture (TikZ, editable)
figures/workflow.tex  Fig. 2 governed tool-call workflow (TikZ, editable)
figures/fig_*.pdf     Figs. 3-5 (generated by scripts/plot_all.py)
data/                 every number in the paper, as CSV/JSON (ColO-RAN results in data/coloran/ and data/e6_*)
scripts/              data adapter, experiments, plotting
```

## What the evaluation uses
* **ColO-RAN** (Polese et al., IEEE TMC 2023; GPL-3.0): real srsRAN stack on the Colosseum emulator,
  7 BSs, 3 slices (eMBB/MTC/URLLC), 3 schedulers x 28 RBG splits. `scripts/coloran_adapter.py` converts the
  per-UE traces into 1-s slice records with **exactly** the columns of the PoC's
  `prepared_network_slicing_dataset.csv`, so the PoC (`TelemetryRecord`, `analyze_sla`, agents, middleware,
  governance) runs **unmodified**.
* The PoC's original dataset (Botez et al., Electronics 2025) is synthetic; it is only used in E5 (memory scaling; the
  memory content is produced by the agents) and in the earlier pilot mentioned in E4.

## Honest scope
* No LLM endpoint was reachable from the build machine: the RIC agents are replaced in E2 by a scripted
  proposer (same tools, same scope, profile learned only from a 200-s history segment (60-260 s) of each trace); the LLM review
  stage is tested with scripted reviewers. `eps` is a stress parameter, not a measured LLM error rate.
* E1-E5 evaluate the PoC **as uploaded** (v1); proposed fixes are measured as harness-side subclasses
  (role binding `G3_role_fix`, memory window W=30) without modifying it.
* The corrected PoC (**v2**: `network-slicing-PoC-v2.zip`, see its `CHANGES_v2.md`) implements those fixes; E3 re-run on
  v2 is in `data/coloran_v2/` (`PROJ_V2=/path/to/v2 bash scripts/run_all.sh`).
* E4 uses live-LLM runs executed by the PoC team on their host (uploaded as `Network-Slicing-PoC-ahmed.zip`,
  `results/run-6..8.txt`); the run documents do not record the model. The fixed revision (v3) is
  `network-slicing-PoC-v3.zip` (`CHANGES.md`, section v3); E3 on v3 is in `data/coloran_v3/`.
* E4 backend B: NVIDIA Nemotron 3.5 Lightning (`openrouter/nvidia/nemotron-3.5-lightning:free`) on the PoC v3.2
  (`results/nvidia-result1.txt` = run-23, `nvidia-run2.txt` = run-24) -> `data/llm_runs_nemotron/`
  (`evidence_check.json` is a manual check of each cited evidence item against `data/ran_knowledge.txt`).
  E3 on v3.2 is in `data/coloran_v3_2/`.
* SLA budgets for ColO-RAN are fixed a priori from the traffic classes (see `coloran_adapter.py`).

## E4 (live LLM agents) tables
Generated from the PoC's MongoDB results by the PoC scripts (run from the PoC root):
```
poetry run python scripts/evaluate_run.py claude-run2 claude-run3 claude-run4 \
  --out results/current-revision --tex <paper>/tables/e4_live.tex --label Nemotron
poetry run python scripts/stability.py stab-nemotron-1 ... stab-nemotron-10 \
  --name nemotron --tex <paper>/tables/e4_stability.tex
poetry run python scripts/compare_models.py <run ids of every model> --name paper \
  --labels nvidia-network-slicing-model=Nemotron,gemini-network-slicing-model=Gemini \
  --tex <paper>/tables/e4_models.tex
```
`main.tex` includes the stability and model tables only once those files exist.
